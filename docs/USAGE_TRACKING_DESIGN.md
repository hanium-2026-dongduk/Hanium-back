# 사용 시간 서버 추적 — 설계 문서

> 요구사항 정의서 v3.0의 PD03("일일 최대 사용 시간 설정", Low)은 "설정"만 정의하고 있고,
> 서버가 실제 사용 시간을 **어떻게 측정할지**는 요구사항에 명시되어 있지 않다. 이 문서는
> 그 설계 공백을 메우기 위해 이번 작업에서 채택한 방식과 그 이유, 그리고 채택하지 않은
> 대안/트레이드오프를 기록한다.

## 구현 상태 요약

- ✅ heartbeat 기반 서버 집계(테이블/API) — 완료, 실DB로 검증됨
- ✅ 재사용 가능한 콘텐츠 제한 미들웨어(`checkUsageLimit`) — 완료, 단위테스트로 검증됨
- ⏳ 실제 동화/퀴즈 라우트에 제한 적용 — **개발자 B 연동 대기** (API_SPEC_USAGE.md의
  "개발자 B 연동 대기" 절 참고). 그 전까지는 콘텐츠 사용을 실제로 막지 못한다.
- ⚠️ heartbeat를 보내지 않는 클라이언트의 화면 체류 시간은 원천적으로 측정 불가(아래
  "무엇을 사용으로 카운트할지" 참고) — 이는 버그가 아니라 heartbeat 방식 자체의 한계.

## 왜 설계가 필요했나

기존 구현(`checkUsageLimit` 미들웨어)은 클라이언트가 `X-Usage-Minutes` 헤더로 스스로
"지금까지 쓴 시간"을 보고하면 그 값을 그대로 믿었다. 이 방식은:
- 헤더를 생략하거나 값을 조작하면 제한을 그냥 우회할 수 있다.
- 애초에 어느 라우트에도 등록되어 있지 않아 아무 효과가 없었다.
- DB 에러 시 조용히 통과(fail-open)시켜, 제한 자체가 인프라 장애 상황에서 무력화됐다.

"서버가 신뢰할 수 있는 방식"이려면 시간의 출처가 클라이언트가 아니라 **서버 시계**여야 한다.

## 무엇을 "사용 시간"으로 볼 것인가

두 가지 후보를 검토했다.

1. **명시적 세션 시작/종료** (`POST /session/start`, `POST /session/end`) — 화면 진입/이탈
   시점에 명확히 호출. 정확하지만, 앱이 크래시하거나 강제 종료되면 "종료" 호출이 영영
   오지 않아 세션이 무한정 열린 채로 남는 문제가 있다(모바일 환경에서 흔함).
2. **주기적 heartbeat** (`POST /usage/heartbeat`, 30~60초 간격) — 클라이언트가 콘텐츠
   화면에 머무는 동안 주기적으로 "살아있음"을 알리고, 서버는 마지막 heartbeat와의 차이만큼만
   누적한다. 마지막 heartbeat 이후 응답이 끊기면(크래시 포함) 그냥 더 이상 누적되지 않을
   뿐이라 자연스럽게 안전하다. 대신 정확도가 heartbeat 간격 단위로 떨어진다.

**heartbeat 방식을 채택했다** (사용자 확인). 크래시/강제종료에 안전하고, 구현이 단순하며,
캡(cap)을 두면 조작 여지도 없기 때문이다.

## 무엇을 "사용"으로 카운트할지 (범위)

이번 저장소에는 개발자 B가 담당하는 실제 학습 콘텐츠 화면(동화 생성, 퀴즈 등)이 아직
구현되어 있지 않다(Week 2~4 범위). 따라서 "정확히 어느 화면에 머무는 동안 heartbeat를
보낼지"는 **프론트엔드 + 개발자 B와 합의가 필요한 정책 결정**이며, 이번 작업에서 임의로
정의하지 않았다. 지금 정한 것은:

- heartbeat 엔드포인트와 누적/차단 로직 자체 (사실대로 기록하는 인프라)
- "인증/보호자 설정 화면은 세지 않는다"는 원칙 (계정 관리 ≠ 콘텐츠 사용)

아직 정하지 않은 것(추후 결정 필요, 아래 "남은 결정 사항" 참고):
- 동화 생성/열람/퀴즈/단어장 중 정확히 무엇이 "사용 시간"에 포함되는가
- 메인 화면·마이페이지 같은 비학습 화면 체류 시간도 포함할지

## 테이블 구조

```
usage_daily_summaries
  usage_summary_id     BIGINT PK AUTO_INCREMENT
  child_profile_id     BIGINT NOT NULL   -- FK → child_profiles, ON DELETE CASCADE
  usage_date           DATE NOT NULL     -- Asia/Seoul 캘린더 기준
  accumulated_seconds  INT NOT NULL DEFAULT 0
  last_heartbeat_at    DATETIME NULL     -- 다음 heartbeat의 delta 계산 기준
  created_at, updated_at DATETIME NOT NULL
  UNIQUE (child_profile_id, usage_date)
```

**세션 로그(개별 heartbeat 이벤트)가 아니라 일일 집계 하나만 둔 이유**: 이번 범위(일일
누적 시간 계산 + 한도 체크)에는 집계값만 있으면 충분하고, 이벤트 단위 로그는 무한정
쌓이는 테이블이라 보관/정리 정책이 별도로 필요하다. 나중에 "몇 시에 얼마나 썼는지" 같은
세밀한 통계(PD02_STAT_02 "누적 학습 시간" 등)가 필요해지면, 이 테이블은 그대로 두고
`usage_heartbeat_logs` 같은 이벤트 로그 테이블을 추가하면 된다 — 지금 만들지 않은 이유는
현재 요구사항에서 근거를 찾지 못했고, 필요해질 때 스키마를 늘리는 편이 안전하다고 판단했다.

## 제한값의 단위: 자녀별 vs 보호자별

집계(`usage_daily_summaries`)는 **자녀 프로필 단위**로 한다(사용자 확인) — `reward_wallets` 등
다른 자녀 활동성 테이블과 일관되고, 자녀마다 실제 사용 패턴이 다르기 때문이다.

다만 **제한값**(`daily_usage_limit_minutes`)은 기존 스키마 그대로 `guardian_settings`
(보호자 계정 단위)에 남겨뒀다 — 이유:
- 스키마 변경 범위를 최소화(이미 존재하는 `PUT/GET /api/guardian/settings` 계약을 유지).
- 결과적으로 "이 보호자의 모든 자녀에게 동일한 한도가 개별 적용"되는 정책이 된다(자녀 간에
  한도를 공유/합산하지 않고, 각자 독립적으로 그 한도까지 쓸 수 있다).

자녀마다 다른 한도가 필요해지면 `daily_usage_limit_minutes`를 `child_profiles`로 옮기는
마이그레이션이 필요하다 — **이번 작업 범위에서는 하지 않았다.**

## 캡(cap) 값: 90초

heartbeat 간격 계약은 30~60초다. 캡을 그보다 넉넉하게(90초) 잡아 정상적인 네트워크
지연/재시도는 손실 없이 인정하면서도, 클라이언트가 heartbeat를 드문드문 보내거나(예: 5분에
한 번) 재생 도중 앱을 백그라운드에 오래 뒀다가 복귀하는 경우 실제 경과 시간보다 크게
부풀려 적립되는 것을 막는다.

## 남은 결정 사항 (제품/프론트엔드와 합의 필요)

1. **heartbeat를 어느 화면/행동에서 보낼지** — 동화 생성 중, 동화 열람 중, 퀴즈 풀이 중만
   포함할지, 앱을 켜놓은 모든 시간을 포함할지.
2. **자녀별 vs 보호자별 한도** — 위 참고. 현재는 보호자별 한도를 자녀마다 개별 적용.
3. 한도 도달 시 UX — 지금은 heartbeat가 403을 반환할 뿐이다. 프론트엔드가 이를 받아 콘텐츠
   화면을 강제로 벗어나게 하는 흐름은 이번 범위에 포함되지 않는다(백엔드 API 계약까지만).

이 세 가지가 정해지기 전까지는 실제 콘텐츠 라우트에 `checkUsageLimit` 미들웨어를 섣불리
붙이지 않는 편이 안전하다고 판단해, 이번 작업에서는 인프라(테이블/heartbeat API/재사용
가능한 미들웨어)만 구현하고 실제 적용 라우트 확정은 미뤘다.
